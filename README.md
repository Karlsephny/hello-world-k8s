# Hello World на minikube - тестовое задание

Простое веб-приложение на Flask, упакованное в Docker-образ и развёрнутое в
локальном кластере Kubernetes (minikube) с 2 репликами и доступом через
`kubectl port-forward`.

## Структура репозитория

| Путь | Назначение |
|---|---|
| `app.py` | Flask-приложение: `/` отдаёт HTML с hostname пода, `/health` — JSON-статус для проверок. |
| `requirements.txt` | Зависимости Python с зафиксированной версией (`Flask==3.0.3`). |
| `Dockerfile` | Сборка образа; порядок `COPY` подобран под кеширование слоёв (см. ниже). |
| `.dockerignore` | Что **не** попадает в build context при сборке образа. |
| `.gitignore` | Что **не** попадает в историю git. |
| `k8s/deployment.yaml` | Deployment на 2 реплики: readiness/liveness-пробы, лимиты ресурсов. |
| `k8s/service.yaml` | Service (`ClusterIP`) — стабильная точка доступа к подам. |
| `diagrams/architecture.drawio` | Схема организации контейнеров и сервисов (открыть на app.diagrams.net). |

## Инженерные решения и их обоснование

**Service: `ClusterIP` + `kubectl port-forward`, а не `NodePort`.**
Диапазон `NodePort` в Kubernetes по умолчанию — 30000–32767. Порт из
задания, 32777, в этот диапазон не входит, поэтому напрямую задать его
как `nodePort` нельзя — кластер отклонит манифест. `ClusterIP` +
port-forward — решение, которое одновременно удовлетворяет требованию
задания ("режим проброса портов") и не упирается в это ограничение.

**Тег образа `1.0.0`, а не `latest`.** Версионный тег даёт
воспроизводимость: тот же тег всегда указывает на тот же набор байт.
Для честной воспроизводимой
сборки это плохо: контейнер может незаметно "уехать" на новую версию
образа, о которой никто не договаривался.

**Порядок `COPY` в Dockerfile: сначала `requirements.txt`, потом
`app.py`.** Каждая инструкция Dockerfile — кешируемый слой. Если
скопировать сразу весь код, а потом ставить зависимости, то любое
изменение кода (даже не связанное с зависимостями) инвалидирует слой с
`pip install`, и зависимости пересобираются заново при каждой сборке.
Разделив копирование, `pip install` переиспользуется из кеша, пока не
меняется сам `requirements.txt` — сборки становятся быстрее.

**`readinessProbe` / `livenessProbe` на `/health` + `resources.requests/limits`
в Deployment.** Добавлены намеренно:
readiness исключает под из-под трафика Service, пока он не готов (без
перезапуска), liveness перезапускает контейнер, если процесс завис.
`requests`/`limits` дают планировщику и kubelet понимание, сколько
ресурсов ожидать от пода и когда его останавливать.

## Откладка

```bash
kubectl describe pod <имя_пода>
kubectl logs <имя_пода>
kubectl get events --sort-by=.metadata.creationTimestamp
minikube dashboard          # визуальный обзор кластера
minikube delete             # снести кластер после завершения работы
```
